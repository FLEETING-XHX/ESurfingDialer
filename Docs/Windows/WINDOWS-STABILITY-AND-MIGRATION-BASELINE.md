## 资源实测基线

下列 MB 均使用十进制，即 1 MB = 1,000,000 字节。实测对象为本地现有 v2.3beta 发布目录和安装包，不是尚未生成的迁移版。

### 安装文件与压缩模型

| 组成 | 发布目录原始大小 | 独立 solid LZMA 模型大小 |
| --- | --- | --- |
| 桌面界面、.NET、图标等 | 179.67 MB | 52.35 MB |
| Java 运行时 | 92.23 MB | 62.78 MB |
| Kotlin 认证 JAR 及依赖 | 43.40 MB | 41.84 MB |
| 全部文件 | 315.30 MB | 157.06 MB（整体模型） |
| 实际 v2.3beta 安装器 | — | **157.74 MB** |

模型以 Python 标准库 LZMA preset=6 压缩排序后的文件字节流，只计输出字节，没有写出安装器或新压缩包。整体模型与实际安装器相差约 0.67 MB；分组模型不是安装器内部精确分摊，单独分组和全体 solid 压缩可能不同。这使保留桌面端后约 52 MB 的基础压缩体积有实测依据，但不代表未来安装包的确定结果。

### 短时进程采样

用独立空账户目录、AutoConnect=false 和隐藏窗口启动现有发布客户端；另外使用现有包内 Java 运行时和 JAR 初始化 JVM/AndroidMock，不发网络请求、不提供 ZSM、不创建认证会话。每个阶段等待 3 秒，再每 0.5 秒采样，共 10 次。

| 阶段 | 平均工作集 | 平均 PrivateBytes（提交量） |
| --- | --- | --- |
| WPF 桌面端，窗口隐藏、无账号 | 127.05 MB | 80.37 MB |
| 仅 JVM 探针 | 35.66 MB | 367.89 MB |
| JVM + 原 AndroidMock，未建立会话 | 99.57 MB | 413.02 MB |
| 桌面端 + 已初始化 AndroidMock，按分阶段测量相加 | **226.62 MB** | **493.39 MB** |

合计不是同时启动认证客户端的实测值，也不是登录后长期运行值。工作集包含共享页，进程相加用于相同口径的工程对照，不能视为独占物理内存。PrivateBytes 是私有已提交内存，不能当作当前驻留 RAM；任务管理器不同视图的“内存”口径也可能不同。JVM 行是包含项，合计不再额外加一次“仅 JVM”。

采样期间 CPU 消耗很低：桌面端约 15.62 毫秒/5.15 秒，两个 Java 阶段约 0 毫秒/5.14 秒；仅说明这次无认证空闲条件，不能据此推定真实心跳、原生会话或恢复时的 CPU。测试创建的进程已结束，不操作原有客户端、账户、系统开机启动项或 Docker。

测量程序及 JSON 仅保存在 Windows 工程忽略目录 `artifacts/resources-20260930`：`measure_package.py`、`ResourceProbe.java`、`measure_memory.ps1`、`package-measurements.json`、`memory-measurements.json`。首次沙箱 javac 关闭现有 JAR 的文件系统时报告权限异常；经工具权限流程在正常用户上下文中完成编译与采样。该环境错误没有记为客户端认证缺陷。

## 去 JVM 后的工程估算

以下是针对尚未实现方案的预算范围，**不是新核心的实测数据或性能承诺**。统一保留现有 WPF 界面、完整离线安装所需 .NET，替换 JVM/Unidbg 和原 ARM 模拟路线；后台工作集按与本次无认证初始化空闲采样近似的条件估算。真实学校动态模块、算法库、缓存、日志、TLS 和运行时间都会影响结果。

| 迁移方案 | 完整压缩安装包估算 | 相对 157.74 MB 的减少 | 桌面与核心合计工作集估算 | 相对 226.62 MB 模型的减少 |
| --- | --- | --- | --- | --- |
| C# 认证库接入现有 WPF 进程 | 55–70 MB | 约 88–103 MB，56–65% | 140–175 MB | 约 52–87 MB，23–38% |
| Go 独立核心 + 现有 WPF | 58–80 MB | 约 78–100 MB，49–63% | 145–185 MB | 约 42–82 MB，18–36% |
| 本机 C/C++/Rust 核心 + 现有 WPF | 55–70 MB | 约 88–103 MB，56–65% | 132–170 MB | 约 57–95 MB，25–42% |

安装包模型由现有桌面端约 52.35 MB 的压缩基础加上新核心、算法依赖、安装器与余量得到。内存模型保留当前桌面端约 127 MB，假定新核心增加约十几至几十 MB，替代本次已初始化 JVM/AndroidMock 的约 100 MB。这些新核心增量仍是工作量/资源预算假设，范围相互重叠，不能据此证明某种语言一定最省。

只更换核心时，C/C++/Rust 也会保留 WPF/.NET 的主体体积；因此没有充分依据宣称完整离线包能降到几 MB，或整个后台只用十几 MB。若进一步改变界面的框架、常驻方式或 .NET 部署方式，必须另建对照模型并计入全部依赖；不能将依赖外置后的“小下载文件”当作同等离线部署的节省。

09-30研究时曾建议Windows优先评估C#，考虑复用.NET环境及减少跨语言通信；Go作为跨平台后台候选。这是历史方案比较，10-24用户已选择C++方向。当前仍需独立评估算法等价、会话隔离和错误边界，不能用历史估算承诺新核心资源或兼容性。

Native AOT 可用于评估独立 C# 核心，官方说明其启动与内存有相应收益，但依赖需要兼容性检查；现有 WPF 的 trimming 支持未启用，不能直接套用整体 AOT 的小体积假设。Go 也存在堆、垃圾回收和内存/CPU 权衡，不能只按 EXE 大小推断运行内存。依据：[Microsoft Native AOT](https://learn.microsoft.com/en-us/dotnet/core/deploying/native-aot/)、[WPF trimming 限制](https://learn.microsoft.com/en-us/dotnet/core/deploying/trimming/incompatibilities)、[Go GC 指南](https://go.dev/doc/gc-guide)。表中具体数值来自本地测量与工程推算，不由这些文档给出。

### 后续每项问题的记录格式

- 稳定问题编号、发现版本、源码提交/工作区状态、实际安装包版本与摘要。
- 触发条件、时间线、失败阶段、脱敏日志和无敏感信息的复现输入。
- 已确认原因与尚未确认假设分别写明。
- 修复行为、影响模块、兼容性边界和必要的代码依据。
- 回归编号、验证命令、实际结果、现场结果及仍未覆盖内容。
- 对C++及其他迁移实现的要求：输入事件、输出状态、报文字节/算法向量、核心存活/写入所有权、取消/释放等不变量。

没有安全固定样本时先记录证据缺口；日志和样本不包含密码、票据、密钥、原始 ZSM 或完整敏感 URL。未来迁移沿用相同问题编号和行为用例，即使文件名/语言改变，也能直接查询原因与验收依据。
