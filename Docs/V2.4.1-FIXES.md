## “可上网却连接中”的修复

对应[现场分析及迁移约束](Windows/WINDOWS-SESSION-OWNERSHIP-ISSUE-2026-10-29.md)的W8/W9/W10：

1. Windows新核心使用实例专属健康文件，旧v2.4仍写共享health.json也不能冒充新实例。新增Job Object、父进程存活监测与stdin EOF退出；附加保护失败会清理并拒绝启动，不留下无人管理的核心。
2. 两端核心对同一状态目录持有进程锁至退出，重复启动不能继续写入。Windows冲突退出码73明确显示占用并暂停恢复；Docker入口捕获73后明确暂停，正常TERM仍可退出。本容器临时冲突标记使健康检查拒绝借用共享快照，自带OpenWrt看门狗也尊重暂停，不再反复拉起。外置autoheal策略仍需部署方独立核对。
3. 外网可达与本核心已认证分别记录。Windows新状态“网络已可用”明确说明当前没有本客户端会话，不再持续“连接中”或因此误恢复；仍保留实例、线程、探测新鲜度及进展检查。
4. Docker健康检查仅对显式、当前、线程/进展有效且新鲜探测成功的无会话在线状态允许健康，不把任意HTTP200或历史成功当成联网证据，也不伪造authenticated=true。
5. Windows恢复预算只有连续两分钟本核心有效认证健康才重置，使用单调时钟；短暂健康或错实例不能无限清零。健康失效诊断区分实例不符、旧快照、时间异常、进程退出和过期；网络恢复时停止累计预计断网，不冒称重新认证成功。

这些是已定位代码缺口的修复。原反馈电脑没有提供修复后的PID/实例及日志，故本轮不能断言已完成该电脑的现场故障关闭，也不能把服务端旧会话与本机孤立进程视为同一原因。

## 每日重登规则

旧的会话时长估计/提前对齐窗口算法被每天一次的日历计划替代，两端规则一致：

| 项目 | 行为 |
| --- | --- |
| 默认 | 开启；UTC+8，04:00～06:00，每天一次 |
| 时间设置 | 开始00～23点，结束00～24点；结束早于开始直接拒绝，不改写原设置；不允许跨午夜窗口 |
| 执行时机 | 到窗口起点执行；窗口内启动可补执行；错过结束时间等次日，不在白天补登 |
| 同一时刻 | 起止相同按定点执行，留1分钟调度窗口；不解释为全天 |
| 当日已有登录 | 窗口内刚完成一次正常认证，计为当日已完成，避免立即重登；关闭计划期间也记该成功，重新开启不重复 |
| 重启与校时 | 发起计划操作前先持久化日认领；进程重启、同日多次检查与时钟回拨不重复发起日计划 |
| 失败 | 计划不反复发起，真实认证失败后仍走普通认证重试/断线恢复；关闭每日开关不取消已经开始的普通恢复 |
| 状态文件异常 | 已知坏账本保守跳过当天并修复；未知较新格式保留原文并暂停日计划；写入失败不冒险发起计划操作 |
| 外网已通但无本核心会话 | 有安全门户上下文才可发起认证；没有入口时明确等待，不猜IP、不注销其他程序会话。不能承诺接管任意外部会话 |

Windows设置页新增每日开关、起止整点输入、保存按钮及字段旁错误提示，沿用现有界面和滚动布局。设置立即发送给运行核心；控制通道不可用会提示“已保存，将于下次连接生效”，不假称关闭已实时生效。导出诊断设置增加每日开关及窗口，不含凭据。

Docker在本轮工作树的`.env`配置：

```dotenv
AUTO_REAUTH_ENABLED=1
AUTO_REAUTH_SAFE_WINDOW_START_HOUR=4
AUTO_REAUTH_SAFE_WINDOW_END_HOUR=6
```

关闭时设置`AUTO_REAUTH_ENABLED=0`。Docker环境变量变更需按部署流程重新创建容器才能应用；本轮没有更改用户真实.env或容器。
