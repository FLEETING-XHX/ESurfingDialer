# type0 / SM4-CBC 现场兼容修复（2026-11-01）

后续现场反馈发现本阶段将请求的末尾NUL约束错误地套用到响应；响应侧已改为末尾NUL可选，详见[后续响应修复](SM4-RESPONSE-FIX-2026-11-01.md)。以下测试数字及测试包描述为本阶段历史记录。

本次修复针对C++原位捕获的模块：19084字节，SHA-256 `79ec708a1ac6be6f611ecbc95744f564a3c1b439643f1cb77ed88a36a7c5b131`，三个失败快照完全相同。它使用type0外层编码，内层是SM4-CBC。此前独立Java工具用固定合成Client-ID取得的18862字节/type3/TEA模块不能代替C++失败时的响应；目前不能证明Client-ID是差异的唯一原因。

## 修复范围

1. type0从payload末尾向前做相邻字节累积XOR，包含payload[0]，无type3的外层去填充。LZMA属性、1MiB输入/目标、16MiB字典限制保持不变。原生LZMA入口Hook与C++/Python恢复出的18938字节输入逐字节一致。
2. 解包得到38652字节ARM32 ELF，整体SHA `6543cf52f5d7afa236d8fdd82ddba86015f9bd84bbf93f7bfaabb115f39dee46`。ZsmInit/Code/DeCode等实现不同于旧TEA模块，不能只放行外层类型继续复用旧算法。
3. 新受控profile为标准SM4-CBC，16字节key、16字节IV。参数来自四处PC引用确认的0xa004数据池（skip160）。S盒、FK、CK、轮函数和密钥扩展与现有参考SM4原语一致，复用sm4_common.c；无现场密钥常量或UUID别名。
4. Code规范化XML后，传UTF-8字节及一个末尾NUL，再按16字节PKCS7填充，输出大写hex；解密严格校验hex、长度、PKCS7及末尾NUL。原生边界32组合成输入覆盖全部填充长度1–16，静态提取参数与运行时指针参数一致。
5. 新profile校验.text/.rodata/.plt和仅屏蔽32字节key/IV的完整ELF摘要 `c75879a06b55fe814cb280cf911d59dd612779463778e32e9bad031a70c1a545`。其它代码、导入、重定位、元数据或布局变化仍拒绝；不执行ARM代码。
6. 外层type0/type3与内层TEA/SM4是两个维度，按各自证据识别，不能认为所有type0都一定是SM4。未知type1/2及其它实现仍不在支持范围。

## 已验证与限制

已验证：现场SM4原件、改头ID、改key/IV三种模块，各21组原生请求和21组独立原生合成响应，C++双向逐字节一致，生产会话链各331项通过。包括两次新会话、ticket/login/连续keep/term、中文/emoji/转义、长度边界、损坏输入和未知代码拒绝。响应黄金值来自原生SM4 primitive，不是C++自身往返。

新增永久SM4标准/原生公开合成参数黄金回归36项；新profile解析正/负例14项，Python新样本24项、旧样本25项。仍需最终构建/包装检查；结果记录在随包OFFLINE-VALIDATION.json。原始模块、私有参数、内存映像和原始对照日志仅保留本地artifacts，不进入源码或测试包。

原生结果在固定glibc Java17、network:none、只读根、非root、无capabilities的隔离容器内取得。不在Windows宿主执行ARM，不调用Inspect或使用真实账户。本机REA的ARM深度provider不可用，静态结论来自本地pyelftools/Capstone及既有反汇编，运行行为由上述隔离Hook核对。

这已修复可在本地复现的缺失编码/算法路径，**不等于真实校园网登录、首次心跳或长期稳定性已通过**。已有type3/TEA路径需要同轮回归；其它模块轮换仍可能需要新增受控profile。

## 路由器测试

本次测试包复用上一modulefix测试包的容器名、Compose项目和状态卷，保留Client-ID/MAC；Kotlin卷不变。解压到新目录，先把上次测试目录的.env复制到本目录，确认NATIVE_EXPERIMENTAL=1，日常测试NATIVE_CAPTURE_BOOTSTRAP=0。

```sh
docker stop ESurfingDialerNative-v3.0.0-modulefix-test
sh install.sh
docker stop ESurfingDialer-v2.4
sh start.sh
docker compose -f compose.native.yml logs --tail 80
```

先看BOOTSTRAP_RECEIVED编码；首次心跳确认后应见LOGIN_CONFIRMED，health.json的phase=online且authenticated=true。浏览器能上网本身不代表C++本会话已认证。确认后观察10–15分钟。

如仍失败或2分钟内未确认首次心跳，停止测试并恢复Kotlin：

```sh
docker compose -f compose.native.yml stop
docker start ESurfingDialer-v2.4
```

如需继续取证，选择短暂断网时段，用`sh start-capture.sh`显式开启C++原位快照，失败一次后`sh export-diagnostics.sh`导出并回退。把results/cpp-XXXXXX整目录下载到本地Log供分析，原始.bin不公开。不要删除旧卷、执行down -v或让两个认证程序并发运行。
