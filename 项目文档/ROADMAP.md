# 未来开发方向

> 本文只记录尚未完成的工作及其优先级。已完成的能力单独列出，不能据此推断其他项目已经提供。

## 已完成：增强连接策略

“增强连接”已完成并进入当前客户端，不再属于后续待办。

- 正常运行时不重复认证。当前增强模式下客户端每 5 秒读取本地健康状态，核心网络检查每 5 秒、常规健康写入每 15 秒；保守模式分别为 10/20/30 秒。异常事件可请求立即写健康状态，具体参数以当前代码为准。
- 认证核心异常退出、健康状态过期、关键线程停止、认证心跳长期未确认或持续掉认证时，监督层才介入恢复。
- 具备启动宽限、连续异常确认、30/60/120 秒退避、最大恢复次数和手动停止取消恢复，避免网络抖动导致反复认证。
- 常态健康轮询不写日志；日志仅记录异常、恢复和达到上限等有价值事件。核心原有的正常心跳与掉认证恢复始终保留。

## 1. 认证协议兼容与会话初始化修复

2026-09-26 开发进度：2.3 源码已完成初始化脱敏诊断、无效原生句柄边界、动态门户入口与有限协议重试，并通过本地回归。现场算法提供者与真实校园网端到端验证仍未完成；详细状态见 [认证修复计划](AUTH-REPAIR-PLAN.md)。

这是当前 Windows 版本的发布阻断项。2026-09-23 的 v2.1／v2.2 日志都显示 ticket 响应到达后无法初始化会话；证据和未确认项见 [Windows 认证会话问题记录](WINDOWS-AUTH-SESSION-ISSUE.md)。先确认现场返回的 ZSM 类型和 Algo-ID，再决定兼容实现，不能把换 UA 或增加重试当成已修复。

- 第一阶段：补齐脱敏诊断。区分门户解析、ticket 网络请求、ZSM 格式、算法标识、原生库加载和登录确认等失败类别；日志只保留必要的元数据，并限制重复错误写入频率。用同一校园网的 Windows、Docker／旧终端与参考 C 项目做对照。
- 第二阶段：让认证入口从当前门户配置发现，并在使用前校验地址、协议和必要参数；保留明确的兼容回退与故障提示。认证通道的 UA、请求体和算法能力必须成套配置，不能只改一个字符串就宣称支持新通道。
- 第三阶段：为 ZSM 增加独立、可测试的格式识别和 Algo-ID 分派层。先实现现场证实需要的算法，再按样本与回归结果扩展；旧算法和原生库可作为受控回退，未知算法要明确失败，不静默重试。加密参数、密钥材料与变体需要按可验证来源逐一核对，禁止根据名称猜测或混用。
- 第四阶段：用无敏感信息的固定测试向量、异常／截断 ZSM、不同通道样本，以及真实校园网端到端测试验证加解密、票据、登录和心跳。至少覆盖 32／64 位差异、网络切换、离线部署、重试上限和旧版本回归；发布前确认 UI 不会永久显示“连接中”。
- 参考 `ESurfingClient-CVersion-2.1.1-r4` 的动态门户发现、算法分派和错误分类思路；当前本地附件已包含动态 ZSM 与 Android 新算法分派路径；各系统运行方式、认证通道和算法能力应分别核对，跨系统可运行不等于各认证通道均已验证。对照发现和已落实的响应/门户/监督修复见 [C 项目对照与修复](C-REFERENCE-REVIEW.md)。若复制代码或算法实现，先核对 Apache-2.0 与第三方许可、保留必要声明和修改记录；优先围绕自己的接口与测试逐步实现。

### 算法层拟采用的结构

将门户发现、ticket 请求、ZSM 头部解析、算法选择、会话加解密和登录流程分成独立边界。算法提供者以经验证的 Algo-ID 注册，明确声明支持的通道、ZSM 格式和所需参数；每次会话持有自己的状态，避免多个账号共享可变密钥。解析器只读取有界长度的必要字段，对截断、未知版本和未知 Algo-ID 返回可识别错误。

短期可在保留现有原生库的同时补齐入口发现和诊断，并只针对已验证的现场算法增加兼容实现。中期优先评估可在 Java 核心及 Docker／未来 macOS 共用的算法模块；若某算法必须依赖本机代码，再隔离到可替换的提供者。只有测试向量与真实认证均通过后，才启用新提供者和受控回退。性能优化应先测量 CPU 与内存；不以删减校验、共用密钥状态或静默切换算法换取速度。

## 2. 稳定性、资源占用与回归保障

协议兼容修复之外，继续优先保障轻量、稳定和低后台开销。

- 在真实校园网、游戏和长时间后台运行场景下采集 CPU、内存、磁盘写入、网络探测和日志增长数据，避免凭感觉调高轮询频率。
- 持续检查认证、心跳、重认证、网络探测和进程恢复的边界条件，优先修复可能造成长时间断网、循环恢复或误判的缺陷。
- 扩充关键路径的回归测试，并覆盖网络切换、休眠唤醒、断网恢复、认证页异常和手动停止等场景。
- 定期清理重复逻辑、过期配置和构建垃圾；明确客户端界面、认证核心、安装脚本和部署文档的职责边界。
- 继续坚持账户信息最小化保存、日志脱敏导出和有限日志读取，防止隐私泄露与长期运行的磁盘膨胀。

## 3. 离线部署、安装包与新手文档

- Windows 客户端和 Docker 软路由版继续优先支持离线安装，避免首次部署依赖临时公网下载。
- 完善截图化、面向新手的部署教程，覆盖安装、配置账户、启动、状态确认、日志导出和常见故障排查。
- 每次发布提供版本说明、适用平台、校验信息和清晰的升级步骤；保留旧安装包名称，不强制重命名或替换历史文件。
- Docker 版本继续降低无公网软路由环境的部署门槛，并保持配置与设备身份文件可安全保留。

## 4. 使用体验与 UI

- 根据实际反馈持续优化主页、账户管理、日志和设置的布局与文案，保持常用操作直观且页面简洁。
- 更清楚地区分连接中、已连接、掉认证、自动恢复和需要人工处理的状态，并通过托盘图标同步展示。
- 优化多账户添加、编辑、切换和删除流程，减少新用户的配置步骤。
- 完善网络状态展示、日志筛选和错误提示，帮助用户判断问题来自账号、校园网、认证页还是本地网络。

## 5. 兼容性与反馈闭环

- 收集不同学校、运营商认证页面及网络环境下的脱敏日志与复现信息，持续改善兼容性。
- 在设置页保留仓库入口；仅在评估清楚安全性、离线行为和用户控制方式后，再考虑检查更新能力。
- 对新的认证异常先形成可复现样本与回归用例，再调整恢复策略，避免针对单一学校做高风险特例。
