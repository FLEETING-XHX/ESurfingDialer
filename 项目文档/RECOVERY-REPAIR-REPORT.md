## 本轮完成内容

| 问题 | 修复结果 |
| --- | --- |
| 已登录后遇到缺 IP 参数的门户只记录错误，无法进入门户恢复流程 | 将带门户地址/内联配置的结果纳入相同防抖策略，允许后续读取最终配置；没有任何门户信息的结果不触发认证 |
| 切到新网络仍受旧会话的登录宽限和重认证冷却限制 | 连续两次发现同一组有效的新用户 IP/AC IP 后申请恢复；单次、交替网络和夹杂成功/错误探测不累计为一致证据。同一网络继续遵守原有宽限与冷却 |
| 网络探测和认证完成可能覆盖待恢复状态 | 恢复请求使用单调版本号；后续网络成功不能清除已接受请求，较早认证完成也不能确认较新请求 |
| 唤醒后直接按旧健康文件恢复，可能提前重启核心 | 接收系统恢复通知后只向已请求且存活的核心发送 `network recheck`，唤醒现有网络/认证等待并请求健康刷新；监督层提供固定 20 秒窗口，用单调时钟计时，不随健康轮询延长 |
| 手动停止后恢复任务仍等到延时结束 | 取消延时任务本身；停止或在待恢复期间关闭增强模式均立即撤销等待。原有进程代数检查继续保留，防止旧账号任务重启 |
| 原生会话可能在使用中被释放，或多次执行释放 | `NativeSessionHandle` 串行化使用与释放，释放只执行一次；即使释放报错也不再次调用 JNI free，释放后的使用返回明确错误。加解密异常只输出分类错误，文本统一 UTF-8 |
| ZSM 诊断与原生加载耦合，动态模块候选信息不足 | 独立 `ZsmHeaderReader`，只读取有界的两个头部字段及固定位置的类型/长度字；记录动态打包格式候选和声明长度，保留原生提供者处理未知布局 |

动态 ZSM 的识别只用于诊断。头部 UUID 可能是模块 ID，不能直接用它选择算法；本轮没有解压、执行模块、导入 C 密钥或启用新算法。完整算法兼容仍对应 [认证修复计划](AUTH-REPAIR-PLAN.md)第 5 项。

## 资源与停止边界

- 保留原有常态网络与健康写入频率，没有增加长期轮询；新增网络检测由恢复通知触发。
- 门户追踪只持有一个候选和有上限的计数，恢复版本号不保存历史请求或账号内容。
- 退出时解除静态电源事件订阅，避免窗口被事件持有。事件生命周期要求参考 [Microsoft 官方文档](https://learn.microsoft.com/en-us/dotnet/api/microsoft.win32.systemevents.powermodechanged?view=windowsdesktop-10.0)。
- 手动停止后，唤醒通知不会重新启动核心；唤醒重查也不清除确定性算法失败的暂停预算。
- 上述是已落实的资源边界；真实认证状态下的 CPU、内存、日志增长与长时间运行测量仍未完成。
