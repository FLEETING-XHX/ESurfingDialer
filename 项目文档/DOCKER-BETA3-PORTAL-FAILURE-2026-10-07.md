旧 `configXml()` 用一个 `catch(Exception)` 包住解析器安全配置、解析器创建与 XML 解析。这些失败都报 `PORTAL_CONFIG_XML_INVALID`；解析器工厂选择的 `FactoryConfigurationError` 还可能直接逸出。因此，旧日志无法区分容器中的解析器初始化问题与真正的 XML 内容错误。

本轮保持原有解析、唯一字段、URL/IP 与安全配置规则，补充以下诊断：

| 错误码/字段 | 含义 |
| --- | --- |
| `PORTAL_XML_PARSER_SETUP_FAILED` / `xmlStage=PARSER_SETUP` | 工厂选择、安全配置或解析器创建失败 |
| `PORTAL_CONFIG_XML_INVALID` / `xmlStage=XML_PARSE` | 解析器报告 XML 解析错误；也可能是 DTD/深度等安全规则拒绝，不等于账号或算法失败 |
| `PORTAL_XML_PARSER_FAILED` / `xmlStage=XML_PARSE` | XML 解析阶段的其他异常 |
| `configChars` | 配置片段字符数 |
| `xmlLine` / `xmlColumn` | 解析器返回的规范化、包装后 XML 输入位置；不是原 HTML 的行列号，未知为 -1 |
| `xmlIssue` | SAX异常在内存映射到固定语法类别，未识别模板为OTHER_XML_SYNTAX；不输出异常文本 |
| `xmlContext` | 在同一规范化输入上定位的TEXT/ATTRIBUTE/START_TAG等固定类别；是报告位置上下文，不保证是最初坏字符 |

不输出异常消息、栈、原始页面、标签/属性值、URL、IP、票据或账号信息。解析失败依然拒绝进入登录，不自动取第一项或绕过配置校验。

### 直接停止容器的注销路径核查（2026-10-08）

用户补充：平时直接停止容器，通常几秒内检测到断认证，极低概率账号显示退出后仍可上网。正式v1.3确实写了停止时尝试注销：入口脚本接收INT/TERM后给后台记录PID发终止信号并等待；Java shutdown hook将运行状态置为停止，存在会话时调用`term()`。会话、注销地址或ticket缺失时直接跳过。它已经有主动注销尝试，是否实际发送、完成和被服务端接受仍需退出时段证据。

v1.3的注销HTTP成功只关闭响应，不解读注销业务结果，也不确认网络侧撤销访问权限。它的连接、读、写各有30秒超时，没有整体请求时限；随包Compose没有显式停止宽限。Docker官方说明Linux容器在未另设超时时默认等待10秒，再发SIGKILL，所以慢退出可能被截断。管理界面或实际容器可以覆盖超时，不能仅由源码认定现场恰为这个原因。[Docker stop文档](https://docs.docker.com/reference/cli/docker/container/stop/)、[Compose停止宽限](https://docs.docker.com/reference/compose-file/services/#stop_grace_period)。

入口脚本通过`su-exec ... sh -c 'java ...'`或后台函数启动Java，未显式`exec java`；只凭源码不能保证每种shell路径记录的PID均直接对应JVM，也不能断言实际发生信号丢失。还需对应Linux镜像的信号转发与退出时序验证。用户报告官方客户端也会低概率复现，不能把所有现象归为本项目的退出实现；服务端/网关下线原因仍未证实。

DOPT-08继续跟踪可靠信号转发、有界注销和停止宽限、固定阶段日志与业务确认。持续联网仍会让诊断返回在线并取不到故障门户；待实际再次需要认证时采集v2。此次仅记录核查，不刷新源码运行行为或原部署包。

## 新v2定位门户兼容问题（2026-10-08）

这次用户重新采集到门户，GET链为302→302→200，HTML26595字节，配置仍为4551字符。故障为`XML_PARSE`第1行1784列、`ENTITY_REFERENCE`、`ATTRIBUTE`，属性中的查询分隔符裸`&`计数为4；其他属性裸`&`、未知实体、截断和控制字符计数均为0。这些证据支持属性内查询串未转义导致实体引用错误，而现有兼容函数只处理标签正文，跳过整个标签。

两处auth都是CDATA、路径类别AUTH_CGI，匿名规范化值组相同；一个是共同根的直接子节点，另一个处于更深层。ticket只有一个，为CDATA/TICKET_CGI。该词法结果不是完整DOM解析；修复时仍需完整安全DOM成功，再逐项校验和比较认证地址，不能拿匿名值组代替校验。
