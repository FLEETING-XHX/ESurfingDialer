# Docker beta2 门户配置失败分析与修复计划

日期：2026-09-28。状态：已实施解析兼容、诊断和恢复修复；实际门户结构与校园网认证待现场验证。

初始分析基线：`codex/docker-beta` / `4f10b0b`（v1.4.0-beta.2）。用户随后授权开始修复；当前改动保留在工作区，未生成新部署 ZIP。

## 已确认的失败位置

用户提供的日志覆盖 14:49:06–14:50:01。应用加载设备身份并启动，随后在 14:49:07、14:49:12、14:49:22、14:49:42 四次认证前置发现过程中失败；最后记录 shutdown，其触发原因未出现在日志中。

堆栈对应当前 [PortalConfiguration.kt](../ESurfingDialer-Docker/01_Docker源码/ESurfingDialer-Docker-Fixed/src/main/kotlin/com/rsplwe/esurfing/PortalConfiguration.kt)：

1. `discover:81`：GET 门户响应，检查 HTTP 成功状态和 128 KiB 长度上限后，调用页面解析。可以确定这次响应通过了这些检查，不代表门户业务配置有效。
2. `parse:48`：执行 `tag("auth-url")`。
3. `parse$tag:44`：正则匹配数量 `values.size != 1`，抛出 `PORTAL_CONFIG_INVALID`。

因此，直接原因是：已识别的门户配置块中，当前解析器没有匹配到唯一的 `auth-url` 字段。匹配数量可能是 0 或大于 1；日志无法区分。

执行已经通过配置块起止标记检查，错误尚未到 `ticket-url`、端点路径或 IP 校验。认证在 [Client.kt:171](../ESurfingDialer-Docker/01_Docker源码/ESurfingDialer-Docker-Fixed/src/main/kotlin/com/rsplwe/esurfing/Client.kt#L171) 发现门户时中断，未执行后面的 `LOGIN_ATTEMPT`、原生会话初始化、ticket 请求、账号密码登录或心跳确认。现有证据不能判断账号密码、原生算法是否可用。

## 现场原因仍待区分

| 可能情况 | 当前代码表现 | 所需证据 |
| --- | --- | --- |
| 配置确实缺少 auth-url，或内容不完整 | 匹配 0 次 | 配置块中字段存在性、闭合状态及页面类型 |
| 字段存在，标签或内容格式与正则不一致 | 匹配 0 次 | 脱敏后的标签结构，例如标签空格/属性、命名、CDATA 与文本混合形式 |
| 同一配置块中重复 auth-url | 匹配大于 1 次 | 字段数量及是否是重复模板或多个不同端点 |
| 门户请求拿到模板、提示页或错误的落地页面 | 配置标记存在，但字段结构不满足要求 | GET 跳转链、最终响应状态/类型、落地路径和配置结构 |

beta2 原正则要求精确的 `<auth-url>` 和 `</auth-url>`，内容只能是一个 CDATA 段或不含 `<` 的普通文本；没有通用 XML 结构解析。它可能拒绝 XML 中合法但未支持的写法。具体现场是否属于这种情况，必须用样本确认。

本地 C 参考附件同样提取这两个配置标记和字段，但其 `xml_parser` 只取第一组精确标签，没有重复字段检查。它不能证明现场字段一定存在，也不能证明直接复制 C 解析器可以解决问题。

## 重复错误的原因

`Client.run:137–143` 将此异常作为一般异常处理，清理状态后继续退避重试。日志中的约 5、10、20 秒间隔与该退避逻辑一致，期间没有再次出现应用启动日志，说明这些是客户端循环重试，不是日志所示的容器反复启动。

在 beta2 基线中，`AuthenticationFailure` 虽带 `deterministic` 标志，Docker 运行代码没有消费它；没有原生会话时 `resetSessionState` 也不会增加 recoveries。相同解析失败因此可能持续重试并输出堆栈。最后的 shutdown 无法据此认定为超时退出或崩溃。

## 实施顺序与完成条件

### 1. 获取同环境门户证据

- 在失败时相同网络和容器环境，以当前 User-Agent `CCTP/Android8_vpn/2082` 进行只读 GET，核对首跳、有限跳转与最终页面。
- 收集响应状态、Content-Type、字节数、配置块数量、auth-url/ticket-url 标签数量、CDATA/文本结构和标签是否闭合。
- 原始页面如需暂存，仅在软路由本地使用受限权限；对外只提供经过脱敏的结构样本。不要上传完整查询参数、用户/AC IP、MAC、client-id、账号、密码、ticket、ZSM 或 cookies。
- 同时确认实际运行镜像版本；现有日志行号与 beta2 基线一致，但日志没有版本输出。
- 完成条件：能够区分字段缺失、重复、格式不兼容和错误落地页面，得到可用于离线复现的最小样本。

### 2. 补齐诊断与错误分类

- 在门户发现和解析边界记录阶段、HTTP 元数据、长度、配置块/字段匹配数量与不含字段值的失败原因。
- 将当前笼统错误细分为字段缺失、重复、配置结构错误等；健康状态保留具体原因。
- 同一候选和错误采用日志合并/限频；候选变化或成功后重置，避免每次重复完整堆栈。
- 完成条件：一次失败即可辨别失败类型，日志不泄露门户参数或认证秘密。

### 3. 根据样本修复发现或解析

- 如果字段存在但表示形式不兼容，优先对配置块使用有长度上限的安全结构解析；支持经样本确认的合法格式，并保留唯一字段、非空值、HTTP(S)、端点路径和 IP 校验。
- 如采用 XML 解析，关闭 DTD、外部实体和外部资源加载；按样本评估配置块是否为完整 XML 或需受控包装，不假定所有页面都是 XML。
- 如果请求到了错误页面，修复当前 UA 下的落地/跳转发现；不从无关正文拼猜认证端点。
- 如果配置重复或残缺，先明确来源与语义；不默认取第一项。保留“无配置且已有合法 IP 才使用旧入口”的回退边界，不因解析失败自动绕过校验。
- 完成条件：现场最小样本能提取正确且唯一的 auth/ticket/IP；无效输入仍拒绝，不误判认证成功。

### 4. 处理持续失败的恢复行为

- 对确定的配置错误使用可控退避与定期重新发现；新的门户候选可重新尝试，避免永久禁用后的无法恢复。
- 与网络暂时错误区分，记录明确的认证前置失败状态；避免靠反复重启容器修复不变的页面结构。
- 完成条件：持续错误不会频繁刷堆栈，页面恢复或网络变化后能够重新进入认证，手动停止仍有效。

### 5. 离线与现场验证

- 首先用现场最小样本复现旧解析失败，确认修复后提取结果。
- 回归正常 CDATA/文本/实体、合法标签格式、缺失/重复/空字段、坏配置块、超大响应、无效 URL/IP、无配置回退及有限跳转；结构解析新增 DTD/外部实体拒绝检查。
- 验证门户失败不会初始化原生会话、发送账号密码或标记 authenticated；持续失败/候选变化/停止覆盖诊断与重试行为。
- 运行 Docker 的 `authenticationRegression` 与必要的状态回归；完成对应 `shadowJar` 构建。是否生成新个人测试包由后续用户指令确定。
- 在软路由检查门户解析成功，再依次检查原生会话、ticket、登录、有效心跳及健康状态。门户解析通过只证明越过当前阻断点；真实认证成功以登录和心跳结果为准。

## 已实施的修复

- `PortalConfiguration.kt`：使用有界 XML 结构解析配置片段/带声明的配置文档，支持标签空白、属性、配置包装、多个 CDATA 片段、CDATA 与文本混合、标准和数字实体。保留普通 URL 中常见的原始 `&key=value` 分隔符兼容，CDATA 不做二次转义。DTD/外部实体/外部资源禁用，XML 深度限制 64，页面长度限制继续保留。
- 唯一字段、非空值、禁止字段内嵌元素、HTTP(S)/端点/IP 校验保留。缺失、重复、空值、结构错误、URL 错误分别返回具体代码；重复配置块和坏配置不会静默使用旧入口。
- 缓存页面失效且有门户 URL 时，重新进行有限 GET 发现；新页面提供有效配置后恢复。新页面也无配置时保留原失败，并用 `cachedConfig=true` 标明字段统计来自缓存，不混淆成新页面内容。
- 新增 `PortalDiagnostics.kt`：只记录长度、配置块和字段数量、HTTP 状态、跳转步数与固定媒体类别，不记录完整 URL、IP、字段值、原始响应或 XML 解析异常文本。`-1` 表示未采集/未知，不能视为零个字段；`hop=0` 表示本地页面解析。
- `Client.kt`：预期认证错误输出单行诊断，同一候选入口/IP 和错误码每 60 秒最多记录一次并汇总抑制次数；页面正文或长度变化不绕过日志限频。继续有界退避和定期发现，候选发生变化可在最多一个 5 秒等待片段后重新尝试；成功后重置失败记录。
- 停止期间的异常处理等待也纳入退出清理；最终健康状态写入前临时清除中断标志，写完恢复，避免 NIO 因中断而留下旧的线程存活状态。
