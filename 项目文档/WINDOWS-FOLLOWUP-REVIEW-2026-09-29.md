# Windows 客户端剩余修复检查（2026-09-29）

范围：当前 Windows v2.3beta 源码；仓库基线 `codex/docker-beta / 4f10b0b`。Windows 产品源码没有未提交改动。Docker 9 月 28–29 日的修复只作设计对照，未移植其协议、UA 或原生库。

结论：此前审查的 Windows S1、W1–W4 仍需修复；本次新增 W5–W7，共 8 项。优先处理联网判定、心跳进展及增强恢复计数，再补门户发现与待认证请求交接。未知 Algo-ID 仍属于待证据事项。

证据分级：W1、W5 用当前 C# 源码构建并执行隔离状态检查；其他项由当前源码控制流与现有回归覆盖情况确认，未在真实校园网复现。编号沿用 [9 月 28 日审查](BETA-CLIENT-REVIEW-2026-09-28.md)。P1 为优先处理的认证/恢复缺陷，P2 为特定条件下的功能缺陷。

## S1：联网探测的成功条件过宽

位置：Windows 核心 `utils/NetworkConnectivity.kt:67–71`；`Client.kt:105–110`。

HTTP 200 正文既没有已知配置块，也没有当前正则识别的 IP 关键词时，`parsePortalBody` 返回 null，调用方立即返回 SUCCESS。登录 HTML、JS 跳转或上游错误页都可能落入此路径，后续探测地址不会继续尝试。没有会话时，认证循环只等待下一次探测，无法开始认证。这不是协议登录成功，而是探测误判。

修复：内置地址按预期状态/正文判定；未知响应继续后续探测或有界门户发现。探测阶段只返回观测结果，避免自行刷新代表网络线程正常的健康字段。保留 Windows 自己的总时限与配置约定。

验收：200 登录页/错误页/JS 跳转不证明联网；首地址异常、后地址有效门户；真正的空 204 和微软预期正文。

## W1：健康文件新鲜不代表心跳仍有进展

位置：`app/ESurfingDialerLite/HealthSnapshot.cs:80–81`、`EnhancedConnectionPolicy.cs:45–46`；核心 `Client.kt:121–144`、`HealthStatus.kt:44–57`。

已登录后，心跳原生加解密挂起不会退出线程；独立健康线程仍会刷新文件。`IsConnectedFor` 只要求 authenticated 和文件新鲜，监督策略又在 authenticated=true 时直接返回无异常。已登录心跳没有独立的阶段开始/完成期限；重认证前的 `term()` 也在新认证阶段标记之前执行，属于同一监督盲区。

隔离检查：构造进程/线程存活、文件新鲜、心跳成功时间为 20 分钟前的快照，当前代码返回 `connected=True, recoveryReason=null`。这是状态判定复现，没有让真实 JNI 卡死。

修复：记录心跳、终止旧会话和原生调用的进展、下一次合法心跳期限；用单调时钟和请求宽限监督。UI 与恢复使用一致的健康结论，不能仅添加一个固定的“距上次心跳 N 秒”阈值。正常服务器心跳间隔不应触发误恢复。

现有回归 `tests/ClientRegression/Program.cs:65–67` 明确接受陈旧心跳下的已认证状态，后续需替换为有合法心跳期限的断言。

## W5：异常计数被“已连接”分支反复清零

位置：`MainWindow.xaml.cs:203–229`、`MainWindow.xaml.cs:256–279`；`EnhancedConnectionPolicy.cs:41–44`。

触发条件是健康文件新鲜、authenticated=true，但 clientThreadAlive 或 networkCheckThreadAlive=false。前半段仍判断 usable=true，调用 `RecordHealthyConnection()`，把连续异常、恢复尝试和耗尽标记清零；后半段策略识别到线程停止，只能将异常计数从 0 增为 1。下一轮重新清零，永远达不到连续两次异常的门槛。

这不仅是陈旧心跳问题。核心认证线程捕获 `InterruptedException` 后正常退出时，会在 finally 中把 clientThreadAlive 改为 false，却不会清除 authenticated；其余线程可继续刷新健康文件，所以存在对应的生产代码路径。

隔离检查调用真实 `MainWindow.RefreshHealthAsync()`，使用合成健康文件和只等待标准输入的替身进程，三轮结果均为：

```text
unhealthyChecks=1 recoveryAttempts=0 status=已连接
```

修复：先计算完整健康结论，再决定是否记为健康/重置预算；关键线程停止不能进入 `RecordHealthyConnection()`。恢复次数只在有效恢复确认后清理。

验收：authenticated=true 分别配合认证线程停止、网络线程停止，连续两轮应进入恢复；同样检查异常状态不能不断重置恢复次数上限。

## W2：门户结构解析和缓存恢复尚未跟进

位置：核心 `PortalConfiguration.kt:40–44`、`PortalConfiguration.kt:65`；`utils/NetworkConnectivity.kt:105–114`；`Client.kt:50–55`。

门户仍用精确标签正则提取 auth-url/ticket-url，无法接受部分合法标签空白、属性、混合 CDATA 与文本结构。内联缓存解析在 GET 之前执行，一旦抛异常便不会重新获取。连续三次同类确定性失败会暂停认证。

另一个联动缺口：从 HTTP 200 正文识别到门户时，只保存 portalBody，没有保存本次响应的 URL。后续即使补上“坏缓存重新 GET”，这条路径也可能缺少可重新获取的地址。

修复：独立适配有界安全结构解析与脱敏错误分类，缓存无效时允许有限重新发现；探测结果同时保留来源 URL。保留 Windows 的有限重试与暂停机制，不直接复制 Docker 通道实现。

验收：合法结构变体、缺失/重复/空字段、实体/DTD/超长限制；坏缓存后取得有效页面；HTTP 200 内联配置的来源地址保留；失败诊断不包含响应正文或敏感 URL。

## W6：请求版本仍未覆盖执行选择与门户快照

位置：核心 `Client.kt:85–102`、`Client.kt:148–161`；`States.kt:18,33–45`；`DialerApp.kt:94–118`。

有两条遗漏路径：

1. `REQUEST_ERROR` 和 `DEFAULT` 分支先于 `forceAuthorization` 判断。心跳达到失败阈值后已有恢复请求和缓存入口，但下一轮网络探测失败时，认证线程继续等待；即使认证端点仍可访问，也不会使用已有有效候选重试。增强监督可能最终重启整个核心，保守模式则持续等待探测状态变化。
2. 请求只存版本，不保存对应门户。已接受入口 B 的恢复请求后，下一次入口 C 的观测可以覆盖全局 `States.portal`，即使 C 尚未满足恢复防抖。认证执行时读取最新全局值，而非 B 的快照；版本仍在，却可能处理了另一个入口。认证进行中 authenticated=false 时，新门户也只更新观测状态，没有建立对应版本请求，较早认证完成后直接写 SUCCESS 可能掩盖这个变化。

因此 REC-02 已实现“版本不被 SUCCESS 清除”仍然有价值，但不能等同于完整的待认证请求队列。

修复：将观测、带版本及候选快照的待认证请求、当前会话分开；有效待办的执行不被普通探测失败无限压住。同入口重复观测可合并，较早认证只能确认自己消费的请求。手动停止、确定性暂停和网络未准备好时仍有明确边界。

验收：心跳阈值失败→探测 REQUEST_ERROR→入口仍可用；已接受 B→单次观测 C→执行目标仍为 B；认证 A 期间接受 B→A 成功不能清除 B；重复同入口不导致认证循环。

## W3：最终跳转中的 IP 参数丢失

位置：核心 `PortalConfiguration.kt:67–79`。

首跳没有 user/ac IP、后续跳转 URL 才带完整参数、最终页面没有配置块时，发现器使用原始 `userIp/acIp` 调用 legacy，未采用最终 URL 的参数。结果可能为 PORTAL_IP_INVALID，或者继续使用旧 IP。

修复：在允许的无配置回退路径解析最终 URL，按完整成对、唯一且有效的参数使用；不要把新旧两组 IP 拼接。

验收：首跳无 IP、末跳完整 IP；末跳重复/不完整/非法 IP；配置块与无配置回退路径分别覆盖。

## W4：增强恢复启动失败后重试中断

位置：`MainWindow.xaml.cs:295–301`、`MainWindow.xaml.cs:219`；`DialerCoreProcess.cs:52–58`。

增强恢复成功停止旧核心后，新进程启动若暂时失败，StartAsync 将 `_requested=false` 并取消恢复。主窗口虽记录“将按退避策略重试”，后续轮询却要求 requested 与 running 同时成立，没有可执行的重试任务。停止旧核心失败也要核对同一连接意图问题，因为 Stop 会先清除 requested。

修复：用统一的、可取消的恢复状态机持有用户连接意图，明确区分手动停止与为恢复停止。启动失败有界重试，手动停止/切账号/关闭增强模式及时取消；不能只改日志文字。

验收：停止成功→第一次启动失败→后续启动成功；恢复时停止失败；退避期间手动停止/切账号；达到上限。

## W7：重复启动客户端会干扰状态与认证

位置：`app/ESurfingDialerLite/App.xaml.cs:12–19`、`AppPaths.cs:7–18`；`MainWindow.xaml.cs:86`；`DialerCoreProcess.cs:65–68`。

启动链没有跨进程单实例保护；同一用户默认共用配置、日志、data/health.json。托盘运行时再次打开快捷方式，可以再启动一个窗口；AutoConnect 开启且有账号时还会启动第二个核心。新核心启动会删除共用 health.json，两个核心随后竞争写入相同的 health.json.tmp/health.json。按启动时间判断无法区分两个同时存活的核心，窗口可能读取另一个核心的认证状态。重复认证是否导致校园网互踢取决于现场策略。

修复：至少按用户及配置根目录限制单实例，重复打开时唤起已有窗口；健康快照增加进程/运行实例标识并严格核对，隔离测试配置仍可独立运行。

验收：托盘运行后重复启动、开机自启与手动启动重合、不同配置目录并存；读取其他实例快照必须被拒绝。此项仅静态确认，本轮未启动两个真实客户端。

## 建议实施顺序

1. **联网与监督**：S1、W1、W5。先解决“不登录”和“假在线但不恢复”。W1 与 W5 共用状态判定，应一起设计。
2. **门户与请求交接**：W2、W3、W6。补齐发现证据、候选快照及确认消费，避免解析修好后仍请求错入口。
3. **恢复入口与多实例**：W4、W7。统一启动/停止意图，限制重复进程，完善恢复次数和取消。
